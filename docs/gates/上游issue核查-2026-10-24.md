## 各条详情

### W-2 → esp-idf #18791（完全复现我们的错误）
- 标题：*ESP32S31 build: error when activate XIP and place bss/noinit into PSRAM, cannot move location counter backwards*
- 报告版本 v6.1-dev，2026-07-29 由 `c566ace1f`（*fix(esp_system): fixes build failure with XIP PSRAM + BSS/NoInit in external memory*，改动 `esp32s31/memory.ld.in` + `ld.ext_ram.sections`）关闭。
- **分支核查（API compare）**：修复在 master（behind），release/v6.1 分叉不含——即 v6.1 线至今未回合。
- **处置建议**：向本地 IDF 检出应用该 commit 的 patch（比我们的 sections.ld 手工补丁更正规），或等 v6.1.x 回合；同时可向乐鑫请求 backport（低价值，issue 已有）。
- 我们的 sections.ld 手工补丁在语义上与官方修复方向一致（rodata 与 ext_ram 的布局次序），官方 patch 落地后应移除手工补丁回归验证。

### W-3 → esp-claw #157（open PR，含修复代码）+ #91（根因分析）
- **#157** *fix: PSRAM-stack flash-cache crash and http_reuse use-after-free*（2026-08-25，open）：`CLAW_TASK_STACK_PREFER_PSRAM` 创建的任务栈在 PSRAM，任务做文件 I/O（fopen/FAT）时 flash cache 被短暂禁用，PSRAM 栈在该窗口不可达 → assert/挂死。**点名受影响任务包括 claw_core 系列（记忆/文件 I/O 任务）**——`claw_mem_extrac` 完全吻合（记忆抽取做持久化 I/O；我们的寄存器转储显示卡在 PSRAM 执行区）。
- **#91**（open，2026-05-19）：全局 `SPIRAM_MALLOC_ALWAYSINTERNAL=0 + FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y` 的默认组合在不能 XIP-from-PSRAM 的板子上首读 flash 即 panic——同一根因的配置层分析。
- **#101**（closed）：HTTP 负载下 PSRAM 泄漏至耗尽挂死（不同缺陷但同一"PSRAM 任务环境脆弱"家族）。
- **处置建议**：把 #157 的 PR 分支作为 patch 应用到 vendor/esp-claw（钉版升级为 9b23c15 + #157，独立提交+回归）；若 PR 冲突大，退而求其次在装配层禁用 claw_memory（Kaleido-Claw 本就计划重构记忆模块）。
- **注意**：修复未合入 ≠ 我们的用法错误；upstream PR 摆了两个月未合，说明 esp-claw 处于快速演进期（vendor-licenses R-5 风险的实证）。

### W-1 → 无上游 issue
- esp-claw 资源生成器 `generate_board_resources.py` 支持的外设类型表缺 `adc`，而 registry 组件 `espressif__esp_boards` 的 esp32_s31_korvo_1 板定义已启用 `adc_oneshot`（esp-claw 仓库内自带的本地板级副本注释掉了该块——上游自己知道不兼容）。
- 检索 adc/korvo/s31 关键词无命中 → **建议我们首发 issue**（附：两个 yaml 的具体位置、生成器报错串、本地副本已注释的对照证据；修复方向：生成器补 adc 类型或 registry 板定义回退）。
