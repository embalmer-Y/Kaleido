# 缺陷 H 结案：启动期 Store access fault（esp_hosted 自启 × 主任务栈 memset 竞态）

2026-10-28 深夜定位并修复。此前多轮误判（热相关/flash 频率/单核竞态/
应用无关/旧 coredump 触发）全部被证伪或重新解释，本文记录完整证据链。

## 1. 现象

上电/复位后链式崩溃：`Guru Meditation (Store access fault)`，MEPC 恒为
`0x4fc1a572`（ROM），若干次后某次启动闯关成功，之后**永久稳定**（板子
可连跑数小时）。用户观感即"频繁闪屏"（每轮重启屏幕重新点亮）。

## 2. 最终根因链（全部实证）

```
esp_hosted 组件用 C constructor 在 main 之前自启
  （managed_components/.../port_esp_hosted_host_init.c:17）
→ SDIO/RPC 任务启动，cache/DMA 维护并发进行
→ esp_startup_start_app() 创建主任务（app_startup.c:83）
→ prvInitialiseNewTask 栈填充 memset(stack, 0xA5, len)（tasks.c:1054）
→ 对合法内部堆地址的 store 撞上共享 cache-sync 引擎瞬态失效窗口
   （P4 HP-SRAM 亦走 L2；espressif/esp-idf#19171 同族，上游 In Progress）
→ Store access fault → panic → 写 coredump → 重启 → 再撞 → 链式
```

**触发因子＝宿主机 CPU 负载**（这解释了全部历史"时段性"假象）：
宿主满载 → USB-CDC 拥塞 → 目标机启动日志打印节奏变化 → 主任务创建
时序相位漂移落入竞态窗。上午（轻载）干净、傍晚（边编译边测）崩，
"凉机仍崩""热机崩"皆是该混杂的投影。**此板复现率量化：同固件
宿主空闲 5/5 干净 vs 宿主 16 核满载 8 Guru/13 次启动（~60%/次）。**

## 3. 关键证据

- panic 寄存器：`MEPC=0x4fc1a572 RA=0x401e18c4 A1=0xa5a5a5a5
  MTVAL=0x4ff831c0`——MTVAL 是**合法内部堆地址**（非 PSRAM 非野指针），
  A1=0xA5 即 FreeRTOS tskSTACK_FILL_BYTE。
- 反汇编（RA 处）：`li a1,165; jalr memset; lw a5,48(s2)`——栈填充现场。
- 回溯符号化：`memset←prvInitialiseNewTask←xTaskCreatePinnedToCore
  ←esp_startup_start_app(app_startup.c:83)←start_cpu0_default`。
- flash 内 coredump（0x910000，已取证 /tmp/stale_coredump.bin）：崩溃
  任务上下文 + esp_hosted 两个 SDIO 任务并发在列。
- A/B/满载对照采样：极简应用（仅 kf 心跳）与完整应用在空闲宿主下都
  干净、满载下完整应用复崩——应用内容不是因子，**时序相位**才是。

## 4. 修复

1. `tools/patches/esp-hosted-defer-init.patch`：停用 esp_hosted 的
   constructor 自启（组件重装后需重放）。
2. `convo_stage_main.c` app_main：全部常驻任务创建完、wifi 启动前
   显式 `esp_hosted_init()`（实测仅 43ms，C5 常电、SDIO 探测快），
   `VL,HOSTED,init,<ms>` 落痕。
3. 复现器入库：`tools/hil/diag_boot_rate.py`（RTS 复位×5 轮、按
   pre_app/in_app/ok 分类、MEPC 提取）。验证方法：宿主满载
   （`for i in $(seq 16); do (while :; do :; done)& done`）+ 采样。

**验证**：修复后满载两轮 10/10 启动零 Guru（修复前同条件 ~60% 崩率）。
