## 2 PSRAM / Flash 预算总表

### 2.1 PSRAM 16MB（16,384KB）分项预算

峰值并发场景（预算目标）：**唤醒监听常驻 + Lottie 动画 + LLM 对话流 + TTS 流播放 + 后台 Lua App** 同时发生。

帧缓冲策略取舍（质量优先下的选择）：
- **RGB565 全帧双缓冲 = 846KB**：460×460×2B=423KB/帧 ×2。edge_agent 默认构建即 RGB565（§1.2），QSPI AMOLED 传输量也减半（50MHz QSPI 下 30-60fps 的前提）。画质代价：1670 万色→6.5 万色，渐变背景可能出现色带（可用 LVGL 抖动/带 dither 的 PPA 输出缓解）。
- ARGB8888 全帧双缓冲 = 1,692KB：+846KB 换取 8bit alpha 与全色深。**不推荐作默认**：触红线（见下行总计），且 QSPI 总线 flush 时间翻倍直接伤帧率；alpha 合成需求交给 Lottie 独立画布与 LVGL 层合成。
- 部分缓冲（如 1/10 屏 42KB×2）：省 RAM 但 esp_lvgl_port 基准显示 <10% 屏严重伤帧率，且 AMOLED 局部刷新撕裂风险——质量优先下排除。

| # | 分项 | 乐观 (KB) | 保守 (KB) | 依据/假设 |
|---|---|---|---|---|
| 1 | LVGL 帧缓冲（RGB565 全帧×2，direct 模式） | 846 | 846 | 像素精确计算（C→可 A 级验证）；ARGB8888 方案 +846KB 不采 |
| 2 | LVGL 附属（LV_MEM 池、字体缓存、图片 decode 缓存） | 128 | 384 | C：按 LV_MEM_POOL 64-128KB + freetype 字形缓存 64-256KB |
| 3 | Lottie/ThorVG（460×460 ARGB8888 画布 846KB + ThorVG 引擎/场景/插值器） | 900 | 1,800 | C：画布精确 846KB；引擎内部保守按 0.1-1MB（复杂路径动画）；**假设同时仅 1 个全屏动画层**，双层再 +846KB |
| 4 | WakeNet/AFE 常驻（BSS+VAD+wn10 int16+I2S DMA） | 1,300 | 1,500 | A：实测 1.3MB；保守列预留 AEC 追加 |
| 5 | esp-claw agent 基座（任务栈×N+HTTP server+WS+TLS 会话+mDNS+技能/上下文缓冲） | 1,500 | 3,000 | C：无板端实测；区间锚点=社区"S3 8MB 无焦虑"（<8MB）+W-3 时期 claw_mem_extrac 在 PSRAM 执行的事实；**第2轮必须实测** |
| 6 | 云 ASR 客户端（WS/HTTP 流 + 16kHz 双声道 int16 环形缓冲 + 分片重传） | 400 | 800 | C：10s 预滚 16k×2ch×2B=640KB 会爆→假设 2-3s 滚动窗 128-256KB + 网络缓冲 |
| 7 | 云 TTS 客户端（opus 解码器 30-60KB + jitter/网络缓冲 + 播放队列） | 300 | 700 | B/C：opus 逐实例 20-50KB（§1.3）+ 队列假设 |
| 8 | Lua VM ×N App（64KB 配额/个，常驻 3-6 个） | 192 | 384 | 设计值（docs/design/kaleido-claw-架构.md §2.4） |
| 9 | 相机 DVP 采集（JPEG VGA 帧缓冲×2；YUYV 模式 614KB/帧） | 200 | 800 | B：V-22 实测 YUYV 600KB；产品选 OV2640 JPEG 后取低值 |
| 10 | 记忆系统（SQLite 页缓存 40-80KB + FATFS 挂载/扇区缓冲 + NAND 驱动） | 130 | 350 | B：§1.3 SQLite/FATFS 数据；含 wear-leveling 工作区 |
| 11 | 系统与音频 I/O（I2S0/1 DMA 环形、TAS5805M、定时器、杂项驱动） | 150 | 300 | C |
| 12 | Wi-Fi/BT/lwIP 缓冲（WIFI_LWIP 外置策略开启） | 300 | 600 | C：IDF 典型 60-120 个 pbuf 外置 |
| — | **小计（动态峰值）** | **6,346** | **11,464** | |
| 13 | heap 碎片化与余量红线（≥15%，不可分配） | 2,400 | 2,400 | 工程红线：碎片化后仍可满足最大单块申请（如 846KB 画布） |
| — | **总计** | **8,746 (8.5MB)** | **13,864 (13.5MB)** | 16,384 − 13,864 = **2,520KB 弹性** |

**结论**：
- 乐观情形余 7.6MB，保守情形余 2.5MB（红线之外）→ **PSRAM 扛得住，但保守情形已无"再加一个大块"的空间**。三个超支触发器（设计红线）：① 帧缓冲改 ARGB8888 全帧双缓冲（+846KB）；② 双 Lottie 全屏层叠加（+846KB）；③ ASR 预滚窗放大到 >5s（+300KB 起）。任一触发即跌穿 15% 红线，需等量裁剪（如动画层限半屏、预滚窗缩至 2s）。
- 风险最大的估算行是 #5（esp-claw 无实测堆数）与 #3（ThorVG 引擎内部无官方数），两行合计不确定度 ±2.3MB——这是第2轮实测的优先目标（§6）。

#### 2.1.1 【V-32 实测回填，2026-10-25，主线 ZCode 补记】

真机实测（docs/gates/V-32-esp-claw真机内存实测.md，A级）修正本表两处：

1. **池基数修正（关键）**：esp-claw 默认 `SPIRAM_XIP_FROM_PSRAM=y`，固件镜像 XIP 占 **4,077KB** → PSRAM 可分配池实为 **12,306.6KB**，非 16,384KB。本表按 16,384KB 排布的"总计 13,864KB 保守值"实际**超池 ~1.56MB**；处置：关闭 XIP（回 flash 执行）或按红线裁剪——已列入方案 v1 §5 收敛动作与 V-35 验证项。
2. **行 #5 修正**：esp-claw 基座实测（含 WiFi/lwIP）：空闲联网占用 2,227.7KB、对话峰值增量 ≤192.2KB → 本行修正为 **乐观 1,600KB / 保守 2,200KB**（原 1,500/3,000；不确定度 ±1.5MB → ±0.3MB）。扣除此修正后保守总计 ≈13,064KB，仍超 12,306KB 池约 758KB。
3. 内部 RAM 实测：free 131KB / min 93.2KB（boot 水位，对话零消耗）；ThorVG 大栈须优先 PSRAM 外置。

## 2.2 Flash 16MB 分区规划

现状锚点：edge_agent.bin 已 4.07MiB（A 级实测）且尚不含 KShell/esp-sr 模型/Lottie 运行时（ThorVG 码量 ~200-400KB，C）/记忆系统。Kaleido 固件预估 4.5-5.2MB（C，假设：裁剪 UVC/HLS/plexer 等未用组件 -0.5~1MB，新增 KShell+Lottie+SR +0.8~1.2MB）。

| 分区 | 大小 | 内容 | 备注 |
|---|---|---|---|
| bootloader+分区表+nvs+otadata+phy | 72KB | 系统头 | 参照 edge_agent 表 |
| **ota_0** | 4.5MB | 主固件 | 预估固件 4.5-5.2MB → **超 4.5MB 即挤压 ota_1**，需压缩 OTA 或裁剪 |
| **ota_1** | 4.5MB | 双槽 A/B | esp-claw 现表两槽各 5M 共 10M，本项目固件若 ≤4.5MB 可保双槽 |
| model | 512KB | wn10 int16（~200KB 级）+AFE 参数+音色嵌入 | 物理映射区，避免随 OTA 重刷 |
| fonts | 2MB | freetype 矢量中文字体 2-3 字重（子集化） | 大字体库放 NAND，Flash 只留系统 UI 常用集 |
| assets | 1MB | 出厂 Lottie 表情包 8-12 个 + 图标 | 大部分动画资产放 NAND（128MB 级） |
| storage(FAT) | ~3.3MB | 配置/Lua App 安装源 staging | 与 edge_agent 3M 口径一致 |

**结论**：Flash **临界可管理**——条件是固件 ≤4.5MB。若失控，退路：①不对称 OTA（ota_1 3MB 仅放精简恢复镜像，C 级方案需验证 esp_ota 回滚约束）；②字体/动画全量下沉 NAND；③启动时从 NAND 搬运 ThorVG 资产。Flash 不构成换芯片理由（P4 同为 16MB Flash 时同样紧张）。

## 3 CPU 核分配与并发场景分析

### 3.1 320MHz 双核绑核建议（C 级，待 G2 实测校准）

| 核心 | 任务（优先级降序） | 理由 |
|---|---|---|
| **CORE0（通信/大脑核）** | ① 音频 DMA ISR（最高，硬实时）② Wi-Fi/lwIP/以太网驱动（IDF 默认核）③ TLS/mbedtls（握手突发；S31 有 AES/SHA 硬加速）④ claw agent 任务（LLM 流解析/JSON/记忆抽取，claw 默认 prio5，栈可 PSRAM）⑤ ASR/TTS 流客户端 ⑥ Lua 后台 App（低优先级，prio≤4） | 网络协议栈与 agent 天然亲和；TLS 握手是突发独占（百 ms 级），可被音频 ISR 抢占 |
| **CORE1（渲染/感官核）** | ① LVGL 渲染线程（esp_lvgl_port timer，prio 4-5）+ PPA 加速调用 ② ThorVG/Lottie 帧步进（prio 3-4，与 LVGL 同核避免帧缓冲锁跨核）③ AFE+WakeNet 常驻推理（prio 5；esp-sr 实时性敏感——若实测 CORE1 吃紧则与 LVGL 对调，见下）④ 摄像头采集任务（事件驱动） | 渲染与推理都是持续 CPU 消费者；关键原则：**唤醒链与 Lottie 不同时贴满同一核** |

补充：I2S DMA 描述符在 PSRAM/内部均可，ISR 必须短。claw_task.c 的 `xTaskCreatePinnedToCoreWithCaps` 已提供逐任务核绑定+栈外置能力（vendor 源码，A 级），无需改上游。

### 3.2 峰值并发场景定量分析

最坏场景：唤醒监听常驻 + 全屏 Lottie 30fps + LLM 对话流（TLS 长连接收包）+ TTS opus 解码播放。

| 负载 | 占用估计（单核 %） | 依据 |
|---|---|---|
| AFE+WakeNet10 int16 常驻 | 20-40%（CORE0 或 1） | C：S31 上无实测 CPU 数（V-04 只测了内存）；按 S3 上 AFE SE+WN 典型值跨架构外推 |
| 全屏 Lottie ThorVG 渲染 | **S31 上 60-100%+（一颗核可能不够 30fps）** | B 级外推：P4 400MHz 上 20fps 已 86%（§1.3）；S31 320MHz 约为 P4 算力的 0.6-0.8×（RISC-V 同 ISA，主频比+缓存差异，C 假设） |
| LVGL 合成+QSPI flush（RGB565） | 15-30% | B：官方基准按像素比缩放 + QSPI DMA 卸载 |
| TLS 会话（握手突发/稳态收包） | 握手 50-80%×0.5-1s，稳态 <10% | C：mbedtls+硬加速经验值 |
| opus 解码（24-48kbps 流） | 5-10% | B：嵌入式实测报告量级 |
| claw agent JSON/流处理 | 5-15% | C |

**结论**：CPU 是比 PSRAM 更紧的资源。**全屏 460×460 Lottie @30fps 在 S31 上大概率超单核**（P4 基准反推），必须采用"动画分级"策略：
1. **T0 日常态**：LVGL 原生动画（transformer/补间）+ 小尺寸（≤1/4 屏）Lottie 循环——CPU 无压力；
2. **T1 交互态**（对话中表情）：半屏 Lottie @24fps——单核 ~50-70%，可行；
3. **T2 高光态**（开箱/触发大动画）：全屏 Lottie @20-24fps，**此态允许降级并发**（暂停后台 Lua、LLM 仅收流不渲染中间表情、唤醒链保持）——定义"动画焦点仲裁"与音频焦点（§3.1 of kaleido-claw-架构.md）对偶；
4. 兜底：复杂动画预渲染为 APNG/JPEG 帧序列放 NAND，PPA+JPEG 硬解播放（CPU 换 IO，S31 有 PPA——17 号报告确认）。

## 4 感官管线设计模式（负责人需求第 5 条）

### 4.1 需求还原

语音助手 = **前端 Agent**：① 能调用其他 App 的能力；② 为其他 App 提供接口，App 的传感器数据（类比人体感官）送进 Agent 作决策数据源；③ claw 作为后端负责创建新 App。

### 4.2 MCP 复用评估（本地源码，A 级）

esp-claw 的 MCP 形态（vendor 源码+官方文档核实）：
- **cap_mcp_server**（components/claw_capabilities/cap_mcp_server/src/cap_mcp_server.c）：HTTP/SSE 传输 + mDNS 局域网发现；**自动把已注册 Capability 映射为 MCP 工具**（docs/src/content/docs/zh-cn/reference-cap/cap-mcp.mdx）。包装 API：`cap_mcp_server_add_tool(tool_defs, count)`，限制：**每工具最多 6 个 string 属性**（cap_mcp_server.h）。
- 底层 mcp-c-sdk v2.0.1（managed_components/espressif__mcp-c-sdk）：**已实现 resource 原语**（include/esp_mcp_resource.h，read 回调式）——cap_mcp_server 尚未包装 resource，按 P3"包裹新组件"原则可在 kaleido 侧补一层，零侵入。
- **cap_mcp_client**：agent 可发现/调用局域网其他 MCP 服务器（mcp_list_tools/mcp_call_tool/mcp_discover）——多设备协同的天然口子。
- **claw_cap 框架**（claw_modules/claw_cap/include/claw_cap.h）：capability 分组注册（JSON schema 入参+execute 回调+生命周期）；已有两个关键治理钩子：
  - `claw_cap_set_llm_authorizer()`——**工具发现与调用的策略门**（正好挂 KApp 8 类权限位图校验）；
  - `claw_cap_set_llm_visible_groups()` / 会话级 `set_session_llm_visible_groups()`——按组/会话裁剪 LLM 可见工具面。
- **claw_event_router**（claw_event_router.h）：发布/订阅事件路由（publish_message/publish_trigger + 文本匹配规则→动作），Lua 侧有 lua_module_event_publisher——**传感器数据总线的现成底座**。

**评估结论：可行性高（9/10）**。"App 向 Agent 暴露能力 = 注册 claw_cap（自动成为 MCP tool）"是 esp-claw 原生路径；"App 数据喂 Agent"用 resource 原语（读式）+ event_router（推式）双通道，全部有现成挂点，无需动 vendor 源码。唯一缺口：resource 包装层 + 事件到 LLM 上下文的注入器（均为 kaleido 新组件）。

### 4.3 可借鉴模式对照

| 模式 | 机制 | 对 Kaleido 的映射 | 采纳度 | 来源（2026-10-25 访问） |
|---|---|---|---|---|
| MCP | host(client)↔server；tools=动作、resources=上下文、JSON-RPC over Streamable HTTP | Agent(host)↔App(server)；tools=App 能力、resources=App 感官快照 | **主干采纳**（esp-claw 原生） | https://modelcontextprotocol.io/docs/concepts/architecture （A） |
| Android | ContentProvider（URI 读结构化数据）≈resource；Intent/BroadcastReceiver≈事件总线；Service+Binder≈tool | KApp 权限位图 ≈ Android permission 检查点在 provider/service 入口 | 借鉴鉴权点位设计 | https://developer.android.com/guide/topics/providers/content-providers （A，通识） |
| ROS topic | 发布/订阅、typed topic、QoS | 传感数据总线形态参照（500Hz 报表→聚合后才进 Agent） | 借鉴"高频原始流不直连 LLM"原则 | https://docs.ros.org/en/humble/Concepts/Basic/About-Topics.html （A，通识） |
| Home Assistant | entity=state+attributes+area；自动化=trigger/condition/action 三段式 | 传感器=entity（id/单位/精度/隐私级）；点火引擎≈HA automation 三段式 | **借鉴 entity 元模型与三段式** | https://developers.home-assistant.io/docs/architecture/entities/ （A，通识） |

### 4.4 数据流草案

```text
正向（感官→大脑）：
App(Lua/C) ──publish──▶ 传感数据总线（claw_event_router 扩展：kaleido_sensor_bus）
   │ 500Hz 报表 → 本地聚合器（滑动窗/阈值/变化率）→ ≤1Hz 事件 + 快照
   ├─▶ 情感引擎 / 点火引擎（本地消费，trigger/condition/action，类 HA 三段式）
   └─▶ Agent 上下文注入器：把"感官摘要"按 token 预算拼进 system prompt
        （拉式补充：Agent 经 MCP resource 按需 read `sensor://<app>/<entity>`）

反向（大脑→App）：
LLM tool_call ─▶ claw_cap_execute ─▶ kaleido 权限闸（claw_cap_set_llm_authorizer
   挂 KApp 8 类权限位图：docs/design/kaleido-claw-架构.md §2.3）─▶ 路由到目标 App 的 cap
   越权 → 错误码 + NVS 审计环形日志（架构 §2.3 已定）

侧向（大脑→创建 App）：
Claw agent（chat coding 生成 Lua+manifest → .kapp 确认安装）—— esp-claw 已有
cap_app_mgr + 文件上传/Lua 执行链（M1 实测全通），零新增设计。
```

### 4.5 隐私与 token 成本控制

1. **本地摘要优先**：全量传感数据永不直接进 prompt；本地聚合器输出结构化摘要（"过去 5 分钟温度 26→29℃，持续上升"），单实体摘要 ≤30 token，全部实体一轮 ≤500 token 预算（C 级设计值，需实测 LLM 效果调）。
2. **数据分级**：entity 元数据带隐私级（public/sensitive/private）；private（如摄像头帧、麦克风原始音频）默认仅本地引擎消费，进云需用户在 manifest/设置中显式授权（对齐 8 类权限中的 `sensor` 位）。
3. **推拉结合省 token**：常态只有越阈值 trigger 进上下文；细粒度数据 Agent 用 resource 按需拉取（一次对话最多拉 N 次，N 可配）。
4. **传输安全**：出云仅经 HTTPS（TLS1.3 已修通，M1 §7）；传感器摘要不含位置/身份字段除非声明。

### 5.1 对照 17 号报告触发条件（docs/research/17-P4C5双芯片方案评估.md §4）

| 触发条件 | 现状 | 判定 |
|---|---|---|
| ① W-4 定位为 IDF/S31 SDK 级且无修复时间表 | W-4 已解（TLS1.3 配置，M1 §7），非芯片缺陷 | 未触发 |
| ② S31 国内模组供应失败 | V-06 询价未回报 | 悬置 |
| ③ G2 期间再出现 ≥2 个 S31 独有阻断级问题 | 灵魂架构带来的是**负载/预算压力**，非阻断缺陷；W-1~W-4 全闭环 | 未触发 |

### 5.2 灵魂架构新增负载下的判定

- **PSRAM**：保守峰值 13.5MB/16MB（红线外仍余 2.5MB）→ **扛得住**，前提是锁死 §2.1 三个超支触发器（RGB565 帧缓冲、单动画层、ASR 预滚 ≤3s）。
- **Flash**：双 4.5MB OTA 槽+资产下沉 NAND → **临界可管理**，条件固件 ≤4.5MB。
- **CPU**：全屏 30fps Lottie 是唯一可能压垮单核的场景 → **临界**，靠动画分级（T0/T1/T2）+ PPA/帧序列兜底可控。
- **综合**：**S31 扛得住**，不需要为此切轨。CPU 与 esp-claw 堆实测是两个最大的未定量。

### 5.3 双轨更新（B 线备案激活条件增补）

维持 17 号报告结论（A 线 S31 主线、B 线 P4+C5 备案不投入），**新增激活条件 ④**：若 G2 动画压测（§6 建议）实测 S31 上 T1 态（半屏 24fps Lottie）单核占用 >85% 且优化（ThorVG 配置裁剪/降帧/区域限制）后仍无法达到"对话表情流畅"的验收线，或 esp-claw 实测堆超出 §2.1 #5 保守值 50% 以上 → 提请 R1 变更评估。P4+C5 在此需求下的量化优势：P4 400MHz（ThorVG 基准直接可比）+ 32MB PSRAM 可选 + H.264/CAM ISP；迁移代价与成本结论不变（17 号报告 §1/§3）。
