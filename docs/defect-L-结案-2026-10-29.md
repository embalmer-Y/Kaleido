# 缺陷 L 结案 — think-TTS×soak 硬锁：aio_ref_get 折返死点死循环（我方纯软件 bug）

日期：2026-10-29。结论先行：**根因不是 esp-aes、不是内部 RAM 枯竭——
是 `aio_ref_get()` 折返封顶误用采音环常量（2^17）对抗 2^19 参考环，
读位恰落 131072 时 `m=0`、`off` 永不前进，wn_feed（prio 6，核 0）
无限紧循环饿死整核。一行常量修复 + TWDT panic 双保险，原配方
（31 秒内 k=0 必死）修复后 soak 跑穿、并发深思正常。**

KM,HOOK,score=0.79 照常（km_rec 在核 1/低优先级仍活）——半瘫而非全死

## 2. 根因（确定性，非概率性）

audio_io.c `aio_ref_get()` 折返封顶（缺陷版）：

```c
uint32_t p = (pos + off) & AIO_REF_MASK;      /* p ∈ [0, 2^19) */
...
if (m > (uint32_t)(AIO_RING_MASK + 1) - p)    /* ← 错用 2^17 */
    m = (uint32_t)(AIO_RING_MASK + 1) - p;    /* p == 0x20000 时 m=0 */
memcpy(out + off, s_ref_ring + p, m * 2);     /* memcpy(...,0) 空操作 */
off += m;                                     /* off += 0 → 永不前进 */
```

- 参考环 2^19（AIO_REF_ORDER=19，32.8s），封顶却用采音环的
  AIO_RING_MASK（2^17，8.2s）。**p 恰为 131072 时 m=0**，循环死锁
  在纯寄存器算术上——不访存、不让出、不越界，任何栈/内存完好。
- 触发算术：播放使 s_ref_w 前进（aio_play 每块 +1600），读位
  pos = ref_w − 3072 每 feed 周期扫环面；gcd(1600, 2^19)=512 且
  133120 % 512 == 0 → **连续播放约每 33 秒必有一次精确落在死点**。
- **TTS/soak 相关性的真解释**：s_ref_w 只在播放（TTS/喊话/提示音）
  时前进；纯听状态下 ref_w 冻结、读位不动，永不中招。此前归因
  "think-TTS×soak 并发 × esp-aes" 是相关误当因果——think 只是
  增加了播放时长（说得越多越快扫到死点）。

## 3. 楔死机理全链（签名逐项闭环）

wn_feed prio 6 核 0 死循环 → 同核 prio 5 的 aio_cap 饿死 → 采音环
干涸（ASR/soak 无输入）→ wn_det（核 1）fetch 报 AFE 环空 → main/
soul/soak 同核低优先级全哑 → IDLE0 饿死 TWDT 连拍；核 1 完全健康
（TWDT 打印、km_rec、websocket 重试都在）。TWDT 未开 panic →
仅打印不恢复，产品哑 >10 分钟。早期一例最终 `VL,CRASH,last=
other_wdt`（ESP_RST_WDT）为长哑后另一看门狗收尾，非独立缺陷。

**排除项**：esp-aes DMA/内部 RAM 枯竭假设证伪——楔死期间零 esp-aes
报错，根因 100% 我方软件。（esp_aes_wait_dma_done 上游存在无超时
裸等隐患，另行登记为上游观察项，非本缺陷。）

## 4. 修复

| # | 内容 | 文件 |
|---|---|---|
| 1 | 折返封顶常量改 `AIO_REF_MASK+1`（本环宽度），m 恒 ≥1 | audio_io.c aio_ref_get |
| 2 | `CONFIG_ESP_TASK_WDT_PANIC=y`（defaults + sdkconfig 就地双写） | sdkconfig.defaults / sdkconfig |

#2 的产品语义：任何未来 prio 楔死 → ≤14s 全量 panic 转储（落
coredump 分区）+ 自愈重启，而不是哑到用户拔电。防御纵深，与 #1
独立生效。

惯用法审计：全库逐一核对 ring/mask 配对（aio_capture_stream、
aio_play、aio_ref_get_strided、cap_task）——仅此一处中招。

## 6. 遗留与教益

- **教条再次成立**："先符号化再归因"。本缺陷从立档到结案挂着
  esp-aes × 内部 RAM 的嫌疑跑了一天，两行 addr2line + 十行算术
  就推翻了。压测日志必须完整落盘（109KB 日志救了这次）。
- 压测固件 ELF 不覆盖原则：build/ 目录在结案验证前保持原构建。
- flash coredump 分区现存一枚 19808B 转储（`last=panic`，校验
  通过）——时间线对应已修的 'h' bind 崩溃，留档未清，下次
  coredume 时自然覆盖。
- esp_aes_wait_dma_done 无超时忙等（IDF v6.1）：上游观察项，
  若未来出现 esp-aes 路径挂死再提报。

## 7. 陪跑战果：缺陷 M（W3 深思收集回调 static 游标溢出）——同会话发现并修复

缺陷 L 修复后 soak 跑穿，**暴露出一直被 L 掩护的另一崩溃**（此前
板子先楔死，轮不到它发作）：

- 现场：验证第 5 轮强制深思时核 1 Load access fault，MEPC=
  prvSelectHighestPriorityTaskSMP（调度器遍历任务表），MTVAL=
  0x61747366（ASCII "fsta"，LLM 回复文本碎片被当指针解引用）。
- 根因：soul_think.c collect_cb 用 `static size_t off` 做流式游标
  ——reply[0]=0 每轮清缓冲但 off 跨轮累计；累计超 THINK_REPLY_MAX
  后 `strlcpy(buf+off, sent, 512-off)` size 下溢成无界写，回复文本
  碾过静态区（含调度器任务链），间歇性取决于各轮回复长度之和
  （实测第 4/5 轮中招）。
- 修复：游标改随调用实例（`struct think_reply {buf,off}`，栈上局部），
  缓冲满返回 false 中止流（ks_llm_chat 契约：false=消费方过载中
  止），parse 拒截尾——回到原设计意图。
- 惯用法审计：全库再无 static 游标累积器。

**两缺陷合流的教益**：缺陷 L（AEC 参考环读）与缺陷 M（深思流收集）
都在"深思×soak 并发"时发作——L 提供 ref_w 扫环的播放流量，M 需要
多轮深思累计；同一压测配方双双现形，但这纯属相关非因果。
